# 발표 대본과 예상 질문

연습용 약 6~8분 분량이다. 수업이 지정한 발표 길이를 의미하지 않으며 실제 배정 시간에 맞춰 줄인다. 슬라이드별 근거는 PPTX의 발표자 메모와 [결과 보고서](../PROJECT_REPORT.md)에 있다.

## 1. Incident Response Agent

안녕하세요. 제공된 Base AI Agent를 개선한 Incident Response Agent를 소개하겠습니다. 서비스 이름과 장애 증상을 입력하면 모니터링과 대응 매뉴얼을 조회해 점검 순서를 안내합니다. 직접 실행하면서 발견한 대상 오류와 답변 근거의 혼동을 중심으로 개선했습니다. 모니터링은 모의 데이터이며 서비스를 실제로 재시작하거나 확장하지는 않습니다.

## 2. 미등록 시스템을 다른 대상으로 진단한 문제

가장 먼저 발견한 문제는 billing-service를 요청했는데 auth-service를 조사한다는 점이었습니다. billing-service는 등록된 대상이 아닙니다. 실제 Ollama 비교에서도 원본이 다른 시스템을 조회하고 수집하지 않은 서비스 의존 관계까지 추정했습니다. 대상이 틀리면 그 뒤의 매뉴얼이나 문장이 그럴듯해도 사용자가 요청한 진단은 아닙니다. 그래서 답변 생성보다 앞에서 대상부터 확인하도록 했습니다.

## 3. 서비스 구조와 기술의 역할

화면은 Vue CDN, API는 FastAPI를 사용합니다. 브라우저는 같은 출처의 프록시로 요청하고 백엔드가 LangGraph를 실행합니다. LangGraph가 계획과 조사, 작성 및 검증의 상태 전이를 담당하고 MCP가 모의 지표와 매뉴얼을 제공합니다. 모델은 Ollama와 OpenAI로 교체할 수 있고 SQLite에 대화를 저장합니다. 이 기반은 제공된 구성입니다. 저는 대상 확인과 답변 검증, 관리자 조회, 사용자 화면을 개선했습니다. MCP는 현재 stdio 방식이며 RAG나 벡터 DB는 추가하지 않았습니다.

## 4. 대상 확인을 LLM 호출 앞에 추가

v2 그래프 입구에서 명시된 서비스나 호스트 이름을 등록 목록과 대조합니다. 미등록 이름을 발견하면 모델과 모니터링을 호출하기 전에 이름 확인 안내로 종료합니다. 등록 대상과 미등록 대상이 섞인 질문도 확인부터 합니다. 대상 오류에 불필요한 추론이 이어지는 것을 막았습니다. 다만 특정 식별자 규칙을 검사하므로 별칭, 이름 생략, legacy v1까지 해결한 것은 아닙니다.

## 5. 관측 결과와 미실행 절차를 구분

기존에는 수집 결과를 한 목록으로 전달해 매뉴얼 지시를 이미 확인한 사실처럼 표현할 여지가 있었습니다. 두 모델 백엔드의 작성 지시를 공통화하고 관측 결과, 미실행 매뉴얼, 모델 추정을 구분했습니다. 답변도 확인된 사실, 추가 확인 사항, 조건부 권고로 나눴습니다. 후속 실험에서는 도구가 제공하지 않는 배포 이력을 조회하라는 문제가 남아 실제 조회 범위도 명시했습니다. 화면은 Ollama 실행 결과이며 현재 CPU와 알림 수치를 구분하고 미수집 자료를 표시합니다. 이 방식은 작성 지시이므로 모든 문장의 정확성을 자동 보장하지는 않습니다.

## 6. 퍼센트 인용 검사와 실패 처리

형식만 맞으면 통과하던 검증에 퍼센트 출처 검사를 추가했습니다. 원본과 개선본에 같은 고정 사례를 적용했을 때 근거 없는 퍼센트 세 건은 모두 통과하던 상태에서 모두 반려됐고 정확한 인용은 유지했습니다. 세 번 실패해도 강제 합격시키지 않고 수집 상태만 안내합니다. 하지만 수치의 존재만 검사하므로 다른 지표에 숫자를 붙이거나 초 단위를 만들어낸 두 사례는 여전히 통과합니다. 이 표는 규칙 테스트이며 실제 LLM 전체 정확도는 아닙니다.

## 7. 채팅 입력과 응답 상태 개선

사용자가 답변의 상태를 이해하도록 화면도 개선했습니다. 예시 질문과 여러 줄 입력을 제공하고, 한글 조합 중 Enter와 중복 전송을 막았습니다. 검증 전 초안은 최종 답변과 구분하고 연결 오류를 안내합니다. 복사와 새 대화, 읽던 위치를 유지하는 스크롤도 추가했습니다. 실제 Chrome 경로와 프론트 이벤트 테스트 여덟 개로 확인했습니다. 화면 개선과 모델의 추론 품질 개선은 구분했습니다.

## 8. 관리자에서 검증 이력과 실행 흐름 조회

관리자는 접근 키로 보호한 조회 화면에서 요청별 처리 시간과 토큰, 검증 이력, 실행 트리, 최종 프롬프트를 확인합니다. 사용자 응답에서는 내부 프롬프트를 분리했습니다. 승인받은 모의 일반 요청과 SSE 요청을 실제 LangSmith에 한 건씩 저장하고 조회했습니다. 이때의 217토큰은 Fake 추정값이므로 실제 모델 사용량으로 해석하지 않습니다. 화면은 별도 현재 프로젝트의 0건 상태입니다. 추적이 꺼져 있으면 새 기록이 쌓이지 않는다는 점도 안내합니다.

## 9. 실제 Ollama 비교와 비용 증가

원본과 개선본에 같은 질문 세 개와 고정 MCP 응답을 적용해 실제 Ollama를 각 한 번 실행했습니다. 미등록 질문은 원본이 다른 대상을 진단했지만 개선본은 호출 없이 확인 요청으로 끝났습니다. 반면 등록 질문은 개선본의 시간과 토큰이 늘었습니다. 원본 혼합 질문은 분석 호출에서 타임아웃이 났고 해당 호출의 토큰은 받지 못했습니다. 불리한 결과와 실패도 포함했으며 반복 수가 적어 일반적인 속도나 정확도 향상률로 확대하지 않았습니다.

## 10. 실제 OpenAI 최종 검증

최종 확인은 실제 OpenAI와 MCP, FastAPI SSE 경로에서 진행했습니다. 등록 질문은 mini 세 번과 quality 한 번, 총 네 번 호출했고 검증 한 번에 합격했습니다. API가 반환한 사용량은 1,697토큰입니다. 현재 CPU 98.8%와 알림 91%를 구분했고 이력과 로그 미수집을 표시했습니다. 미등록과 혼합 질문은 API 호출 없이 이름 확인으로 끝났고 세 경우 모두 최종 답변과 DONE을 받았습니다. 브라우저와 프록시는 제외한 실행이며 Ollama와 실험 조건이 달라 속도를 직접 비교하지 않았습니다.

## 11. 남은 한계와 추가 개선

퍼센트 존재 검사는 지표와 서비스 귀속까지 판단하지 못합니다. 실제 로그와 배포 이력도 없으므로 근본 원인을 확정할 수 없습니다. 검증 전 초안은 표시를 구분했지만 노출 자체는 남아 있고 OpenAI 호출부는 모델의 토큰별 스트리밍이 아닙니다. 다음 개선 후보는 구조화된 근거 검증과 실제 관측 도구, 대상 확인 범위 확장입니다. 문서 선택 문제가 커지면 RAG를 검토할 수 있습니다.

## 12. 문제 해결 과정에서 배운 점

가장 큰 교훈은 검증의 경계를 정확히 정하는 것입니다. 대상 오류는 그래프 입구에서 막아야 했고, 그래프 단위 검사만으로는 화면의 동작을 보장하지 못했습니다. 실제로 빈 노드 업데이트가 SSE를 끊어 서버 처리와 회귀 테스트를 보완했습니다. 매뉴얼은 관측 결과나 도구 기능 명세를 대신하지 못한다는 점도 배웠습니다. 규칙 테스트와 모의 연동, 실제 모델 측정을 구분하고 실패와 비용 증가를 함께 기록했습니다. 자세한 코드와 실험 근거는 저장소의 결과 보고서에서 확인할 수 있습니다.

## 예상 질문

**Q. 기존 제공 기능과 직접 만든 부분은 무엇인가요?**

Vue·FastAPI·LangGraph·MCP·SSE·SQLite·모델 교체·LangSmith 추적 코드가 기존 기반입니다. 대상 확인, 근거 구분과 퍼센트 검사·실패 처리, 빈 업데이트 대응, 관리자 인증·조회 UI/API, 내부 프롬프트 분리, 채팅 사용성, 회귀 테스트와 비교 실험을 개선했습니다.

**Q. RAG나 벡터 DB를 왜 안 붙였나요?**

현재 재현한 핵심 오류는 검색 누락보다 대상 선택과 근거 해석 문제였습니다. 매뉴얼은 소수의 정적 문서를 MCP Resource로 선택합니다. RAG는 개선 후보로 남겼고 문서 규모와 선택 품질 문제가 생기면 별도 비교가 필요합니다.

**Q. MCP는 별도 서비스인가요?**

현재는 API 프로세스가 stdio로 두 MCP subprocess와 통신합니다. HTTP 기반 독립 서비스로 배포한 것은 아닙니다. Tool·Resource·Prompt의 역할과 네트워크 서비스 분리를 구분했습니다.

**Q. 검수 합격이면 실제 원인도 맞나요?**

아닙니다. 길이·번호 형식과 근거 내 퍼센트 존재 여부를 검사합니다. 지표 귀속과 자연어 인과 주장까지 자동 검증하지 않습니다. 로그·시계열·배포 이력 없이 원인을 확정하지 않도록 작성 지시를 보완했습니다.

**Q. 등록 질문이 느려졌는데 개선이라고 할 수 있나요?**

미등록 대상의 잘못된 조사와 근거 없는 수치의 통과를 줄이는 데 초점을 뒀습니다. 등록 질문은 시간·토큰이 늘었다는 비용을 보고했습니다. 이후 반복 측정과 출력 최적화가 필요하며 전반적인 속도 향상은 주장하지 않습니다.

**Q. SSE와 모델 스트리밍은 같은가요?**

SSE는 서버가 브라우저에 이벤트를 보내는 전달 방식입니다. OpenAI 백엔드의 현재 구현은 non-stream 모델 응답을 받은 뒤 한 번에 콜백으로 전달하며, 단계 이벤트는 별도로 전달합니다. OpenAI 토큰별 스트리밍까지 구현했다고 설명하지 않습니다.

**Q. 관리자에 기록이 왜 없나요?**

현재 프로젝트가 맞는지, 요청 당시 추적이 켜져 있었는지 확인합니다. 기존 대화는 소급 기록되지 않습니다. 모의 연동 검증 프로젝트와 현재 일반 프로젝트는 다르며 기본 추적은 꺼두었습니다.

**Q. API 사용량과 비용을 어떻게 계산했나요?**

OpenAI 검증의 1,697토큰은 실제 API `usage` 합계입니다. 앱의 `cost_usd`는 단순화된 가상 단가라 실제 청구액과 다릅니다. 청구액은 별도로 조회하지 않았습니다. Fake 토큰도 추정치로 구분했습니다.

## 코드 설명 준비

- `agent/graph.py`: 대상 확인의 조기 종료, 검증 재시도·실패 분기
- `agent/grounding.py`: 관측/절차/추정 구분, 퍼센트 출처와 검사 한계
- `server.py`: 빈 스트림 업데이트 처리, 사용자·관리자 응답 분리와 프로젝트 범위 확인
- `web_chat.html`: 전송 잠금, 요청 구분, 초안·최종·오류 처리
- `eval/compare_ollama.py`, `eval/check_openai.py`: 통제 조건의 차이와 결과 해석
