## 1. 소개 — 10초

안녕하세요. 광주 2반 G065 정인제입니다. 제공된 장애 대응 에이전트의 대상 오류와 답변 신뢰성을 개선했습니다.

## 2. 기존 문제 — 20초

미등록 billing-service를 질문했는데 원본은 auth-service를 조사했습니다. 매뉴얼의 점검 절차도 확인한 사실처럼 표현할 여지가 있었습니다. 대상과 근거가 틀리면 문장이 자연스러워도 진단으로 믿기 어렵다고 봤습니다.

## 3. 구조와 기술 — 30초

기반은 Vue, FastAPI, LangGraph, MCP입니다. 제공된 Supervisor 방식 그래프가 계획·조사·분석·작성 역할을 나누고 추가 조사와 재작성을 제어합니다. MCP Tool은 모의 지표, Resource는 매뉴얼, Prompt는 절차를 제공합니다. 기존 의존성 주입 구조를 활용해 테스트에서는 모델과 도구를 바꿨습니다. 이 기반 위에 대상 확인과 근거 검증, 관리자 화면을 보완했습니다.

## 4. 대상 확인 — 20초

그래프 입구에서 명시된 시스템명을 등록 목록과 대조합니다. 미등록이 포함되면 모델과 모니터링 호출 전에 이름 확인으로 종료합니다. 등록·미등록 혼합 질문도 보류합니다. 화면의 billing-service 안내가 이 동작입니다.

## 5. 근거 구분 — 30초

두 모델 백엔드의 작성 지시를 공통화해 관측 결과, 미실행 매뉴얼, 모델 추정을 구분했습니다. 답변은 확인된 사실, 추가 확인 사항, 조건부 권고 순서입니다. 현재 CPU와 과거 알림 수치를 구분하고, 로그와 배포 이력은 미수집으로 표시합니다. 도구가 제공하지 않는 자료는 별도 요청하며 확장이나 롤백을 실행했다고 말하지 않습니다.

## 6. 수치 검수 — 25초

형식 검사에 근거 내 퍼센트 존재 여부 검사를 추가했습니다. 같은 고정 사례에서 근거 없는 수치 세 건은 모두 통과하던 상태에서 모두 반려됐고 정상 인용 세 건은 유지했습니다. 세 번 실패하면 강제 합격 대신 수집 상태만 안내합니다. 이 수치는 규칙 사례의 결과이며 전체 LLM 정확도는 아닙니다.

## 7. 화면 개선 — 15초

검정·흰색 다크 화면에 예시, 다중 줄 입력, 복사와 새 대화를 추가했습니다. 중복 전송과 한글 조합 중 Enter를 막고 검증 전 초안, 최종 답변, 연결 오류를 구분합니다.

## 8. 관리자 — 20초

LangSmith 기록을 접근 키로 보호한 관리자 화면에서 조회합니다. 검증 이력과 실행 트리, 프롬프트를 확인하고 사용자 화면에서는 프롬프트를 분리했습니다. 실제 저장·조회는 승인된 모의 요청 두 건으로 검증했습니다. 이때 토큰은 Fake 추정치로 실제 모델 사용량과 구분했습니다.

## 9. 전후 실측 — 30초

실제 Ollama는 동일한 세 질문과 고정 도구 응답으로 원본과 개선본을 각각 한 번 실행했습니다. 미등록 질문은 잘못된 진단 대신 모델 호출 없이 확인 요청으로 끝났습니다. 반면 등록 질문은 32.16초에서 40.06초로, 토큰도 2,027에서 2,414로 늘었습니다. 혼합 질문의 원본은 타임아웃도 발생했습니다. 속도 개선으로 포장하지 않고 실패와 비용 증가를 함께 기록했습니다.

## 10. OpenAI 최종 확인 — 20초

실제 OpenAI, MCP, FastAPI SSE 경로도 확인했습니다. 등록 질문은 API 네 번, 1,697토큰으로 검증을 통과했습니다. 미등록과 혼합은 API 호출 없이 종료했습니다. 브라우저는 제외한 단일 실행이며 Ollama와 조건이 달라 모델 간 속도를 비교하지 않았습니다.

## 11. 한계와 다음 개선 — 30초

퍼센트 존재 검사로는 다른 지표에 붙인 숫자와 시간 단위 오류를 막지 못합니다. 모니터링은 모의 데이터이고 실제 로그나 조치 도구도 없습니다. RAG·벡터 DB와 LLM-as-a-Judge는 구현하지 않았습니다. 현재 검수는 규칙 기반입니다. 다음에는 지표와 출처를 구조화해 검증하고 실제 관측 도구를 연결하겠습니다. 문서가 늘면 RAG의 검색 품질과 추가 비용을 비교할 필요가 있습니다.

## 12. 교훈 — 20초

대상 오류는 추론 전에 차단하고 검수 합격의 범위를 정확히 정해야 한다는 점을 배웠습니다. 그래프 테스트를 통과해도 빈 업데이트 때문에 실제 SSE가 끊겨 API 회귀 검사까지 보완했습니다. 재현, 작은 수정, 경로별 검증, 한계 기록이 이번 작업의 핵심이었습니다. 감사합니다.

## 예상 질문

**Q. 기존 제공 기능과 직접 만든 부분은 무엇인가요?**

Vue·FastAPI·LangGraph·MCP·SSE·SQLite·모델 교체·LangSmith 추적 코드가 기존 기반입니다. 대상 확인, 근거 구분과 퍼센트 검사·실패 처리, 빈 업데이트 대응, 관리자 인증·조회 UI/API, 내부 프롬프트 분리, 채팅 사용성, 회귀 테스트와 비교 실험을 개선했습니다.

**Q. RAG나 벡터 DB를 왜 안 붙였나요?**

현재 재현한 핵심 오류는 검색 누락보다 대상 선택과 근거 해석 문제였습니다. 매뉴얼은 소수의 정적 문서를 MCP Resource로 선택합니다. RAG는 개선 후보로 남겼고 문서 규모와 선택 품질 문제가 생기면 별도 비교가 필요합니다.

**Q. MCP는 별도 서비스인가요?**

현재는 API 프로세스가 stdio로 두 MCP subprocess와 통신합니다. HTTP 기반 독립 서비스로 배포한 것은 아닙니다. Tool·Resource·Prompt의 역할과 네트워크 서비스 분리를 구분했습니다.

**Q. 검수 합격이면 실제 원인도 맞나요?**

아닙니다. 길이·번호 형식과 근거 내 퍼센트 존재 여부를 검사합니다. 지표 귀속과 자연어 인과 주장까지 자동 검증하지 않습니다. 로그·시계열·배포 이력 없이 원인을 확정하지 않도록 작성 지시를 보완했습니다.

**Q. 등록 질문이 느려졌는데 개선이라고 할 수 있나요?**

미등록 대상의 잘못된 조사와 근거 없는 수치의 통과를 줄이는 데 초점을 뒀습니다. 등록 질문은 시간·토큰이 늘었다는 비용을 보고했습니다. 이후 반복 측정과 출력 최적화가 필요하며 전반적인 속도 향상은 주장하지 않습니다.

**Q. SSE와 모델 스트리밍은 같은가요?**

SSE는 서버가 브라우저에 이벤트를 보내는 전달 방식입니다. OpenAI 백엔드의 현재 구현은 non-stream 모델 응답을 받은 뒤 한 번에 콜백으로 전달하며, 단계 이벤트는 별도로 전달합니다. OpenAI 토큰별 스트리밍까지 구현했다고 설명하지 않습니다.

**Q. 관리자에 기록이 왜 없나요?**

현재 프로젝트가 맞는지, 요청 당시 추적이 켜져 있었는지 확인합니다. 기존 대화는 소급 기록되지 않습니다. 모의 연동 검증 프로젝트와 현재 일반 프로젝트는 다르며 기본 추적은 꺼두었습니다.

**Q. API 사용량과 비용을 어떻게 계산했나요?**

OpenAI 검증의 1,697토큰은 실제 API `usage` 합계입니다. 앱의 `cost_usd`는 단순화된 가상 단가라 실제 청구액과 다릅니다. 청구액은 별도로 조회하지 않았습니다. Fake 토큰도 추정치로 구분했습니다.

**Q. LLM-as-a-Judge도 적용했나요?**

아닙니다. 현재는 형식·퍼센트 존재 여부의 결정적 규칙 검사와 수동 답변 검토입니다. LLM 평가자를 쓰려면 평가 기준·사람 판정과의 일치도·추가 호출 비용을 별도로 검증해야 합니다. LangSmith 트레이싱 자체를 LLM-as-a-Judge라고 설명하지 않습니다.

## 코드 설명 준비

- `agent/graph.py`: 대상 확인의 조기 종료, 검증 재시도·실패 분기
- `agent/grounding.py`: 관측/절차/추정 구분, 퍼센트 출처와 검사 한계
- `server.py`: 빈 스트림 업데이트 처리, 사용자·관리자 응답 분리와 프로젝트 범위 확인
- `web_chat.html`: 전송 잠금, 요청 구분, 초안·최종·오류 처리
- `eval/compare_ollama.py`, `eval/check_openai.py`: 통제 조건의 차이와 결과 해석
