# 실제 Ollama 비교 답변 검토

2026-10-20 실행한 [자동 측정 결과](ollama_comparison.md)와 [원시 JSON](ollama_comparison.json)을 코드·고정 데이터와 대조했다. 코딩 에이전트가 원문을 확인한 기록이며, 별도의 심사 모델이나 독립 평가자의 평가는 아니다. JSON의 `manual_review: 미검토`는 자동 실행 시점의 상태이고, 후속 검토 내용은 이 문서에 남긴다.

## 관찰 결과

| 질문 | 원본 | 개선본 |
|---|---|---|
| 등록된 payments-service | 32.16초, 2,027토큰, 검증 1회 통과 | 40.06초, 2,414토큰, 검증 1회 통과 |
| 미등록 billing-service | 54.30초, 2,670토큰. auth-service를 조회하고 그 결과로 답변 | 0.0024초, LLM·모니터링 호출 없이 시스템명 확인 요청 |
| payments-service와 billing-service 혼합 | 305.59초 후 `ReadTimeout: timed out`. payments-service 조회 후 분석 호출에서 실패 | 0.0022초, LLM·모니터링 호출 없이 시스템명 확인 요청 |

6회 실행 중 5회는 최종 응답을 반환했고 원본 혼합 질문 1회는 실패했다. 혼합 질문의 원본 토큰 1,169개와 호출 2회는 **응답이 완료된 route·plan만의 합계**다. 타임아웃이 난 analyze 호출도 별도로 시도했으며 해당 호출의 사용량은 받지 못했다. 따라서 이 값은 전체 토큰 사용량이 아니다. 원본의 실패 시간을 성공 응답의 속도와 같은 지표로 평균 내지 않는다.

개선본의 미등록 요청 시간은 대상 확인 노드만의 그래프 실행 시간이다. 실험 도구의 별도 워밍업이나 웹 전달 시간은 포함하지 않는다. 자동 비교표의 미등록 집계는 오류 없는 실행만 대상으로 하므로 원본 분모가 1건이다. 실패한 혼합 질문까지 보면 원본은 미등록 대상 포함 2건 모두 확인 안내 없이 조사 단계로 진행했고, 개선본은 2건 모두 확인 안내로 종료했다.

## 등록 대상 답변

| 확인 항목 | 원본 | 개선본 |
|---|---|---|
| 요청 대상 및 관측 수치 인용 | payments-service, CPU 91.0%, 메모리 55.0%로 일치 | 동일하게 일치 |
| 로그 미수집 상태 표시 | 로그를 분석할 필요가 있다고 표현. 이미 분석했다고 단정하지는 않음 | `로그 미수집`과 패턴 `확인 불가`를 명시 |
| CPU 지속시간 미확인 표시 | `CPU 90% 이상 지속 시`라는 조건을 유지하나 지속 여부 미확인은 명시하지 않음 | 단일 시점이며 지속 여부 확인이 필요하다고 명시 |
| 조치와 실제 수행의 구분 | 확장 절차를 제시하며 수행 완료라고 말하지 않음 | 조건부 권고로 나누고 지속 여부·배포 시점 확인을 요구 |
| 현재 CPU와 알림 CPU의 혼동 여부 | 판정 보류 | 판정 보류 |

현재 CPU와 알림 CPU가 모두 91%인 데이터이므로 마지막 항목의 구분 능력은 이 실험으로 판단할 수 없다. 두 답변 모두 이 사례에서 근거 없는 퍼센트를 새로 만들지 않았고 재작성도 없었다. 따라서 실제 모델의 수치 오류율 감소나 재작성 횟수 감소는 입증하지 못했다. 검증 규칙의 반려 동작은 [별도의 합성 사례 비교](rule_comparison.md)에서 확인한 결과다.

개선본은 미확인 사항을 더 명시했지만 등록 질문에서 시간과 토큰이 늘었다. 추가 지시와 길어진 답변이 있는 설계의 비용을 보여주는 단일 관찰이며, 원인을 각각 분리 측정한 것은 아니다. 일반적인 정확도·속도 개선률을 계산하지 않는다.

남은 문제도 있다. 개선 답변은 `get_monitoring_status`로 최근 배포/트래픽 변화 시점을 확인하도록 제안하지만, 현재 도구가 반환하는 값에는 그 이력이 없다. 해당 확인에는 추가 수집 도구가 필요하다. 이번 실험 중에는 제품 코드를 추가 수정하지 않았다.

## 미등록 단독·혼합 질문

- 단독 질문: 원본은 billing-service 대신 auth-service를 조회했다. 최종 답변의 `이에 의존하는 서비스(예: billing-service)`라는 관계는 고정 데이터에 없고 실제 의존 관계를 조회하지도 않았다. 개선본은 billing-service가 미등록임을 안내하고 확인을 요청해 기준을 충족했다.
- 혼합 질문: 원본은 등록된 payments-service를 조회했지만 billing-service 누락을 확인하지 않고 분석으로 진행했다. analyze 호출이 HTTP 읽기 타임아웃으로 실패해 최종 답변 품질은 판정할 수 없다. 개선본은 billing-service 확인을 먼저 요청해 기준을 충족했다.
- 미등록 대상이 섞이면 등록 대상 진단도 함께 보류하는 것이 현재 정책이다. 부분 진단을 원하는 사용자에게는 추가 질의가 필요하다는 트레이드오프가 있다.

## 한계와 배운 점

- 사례당 1회인 소규모 비교다. 동일 모델·질문·고정 데이터로 조건을 맞췄지만 캐시·메모리·다른 작업의 영향을 완전히 제거하지 못한다.
- 실제 모델과 그래프를 실행했지만 MCP 전송·브라우저·SSE·SQLite까지 포함한 통합 실험은 아니다. 관리자 모의 연동 검증과도 별개다.
- 300초 타임아웃이 발생한 정확한 원인은 확인하지 못했다. 모델의 내부 추론, 서버 상태 등을 추가로 조사해야 하며 원인을 단정하지 않는다. 코드에는 HTTP 타임아웃이 있으나 출력 토큰 상한은 없다.
- 답변 형식 검증 통과는 올바른 대상·원인·도구 능력을 보장하지 않는다. 실행 대상, 원문, 실패한 호출과 사용량 누락까지 함께 봐야 한다.
- 보고서에는 확인 안내의 효과, 미확인 사항의 명시, 등록 질문의 시간·토큰 증가, 타임아웃과 잔여 한계를 함께 제시한다. 이 결과만으로 RAG나 벡터 DB의 필요성은 입증되지 않는다.
